## 2026-10-16：采纳 PL 存储交叉批评的界面措施

针对 `character-campaign-storage-review.md` 第二轮对异步保存与事件顺序的批评，新增编辑器 I/O 互斥：本地加载、文件导入、本地保存与历史导出不能并行替换读取上下文；导出当前文件和正常角色操作仍可进行。加载与导入不再能在都读到空编辑器后先后覆盖角色。

本地保存只确认发起时捕获的不可变档案引用，而非异步返回时的当前档案。界面单独显示“当前进度是否已保存本地”；保存中新增操作仍显示未保存，可以再次保存。未改动时不重复提交严格追加存储事务。成功提交后列表刷新失败，提示已保存但刷新失败，不再谎报“未保存”。浏览器存储仍不是永久备份。

历史列表仅在读取的 token 与当前编辑器确认的存储基线一致时启用；另一页面改变基线则清空并停用列表，不自动接管新 token，也不覆盖内存角色。既有 CAS 和分支/历史保护不变。

新增 `test-core-editor-io.ts` 使用可控 Promise 验证互斥、拒绝并发任务体、失败后释放以及保存旧快照不确认新编辑的约束。它不模拟真实 IndexedDB 配额、跨窗口调度或 DOM 事件，后者仍需独立浏览器验收；不以这一小范围单测认证整个恢复系统。

实际浏览器验收：导入已下载的虚构角色，显示本地未保存；首次保存为 generation 1，随后保存按钮禁用。第二个同源标签页加载同一版本，两页分别新增 1 cp 和 2 cp 事件，均立即显示未保存。对两个真实保存按钮发出并行点击请求：B 成功保存 generation 2；A 报冲突，仍保留 161 cp 和可导出的自身事件，B 为 162 cp 且显示已保存。刷新 B 再从数据库加载，仍为 162 cp；A 再次尝试保存继续拒绝，主件不被覆盖。A 的候选已实际下载为独立文件。未捕获控制台错误。

这是实际同源双标签页的竞争保存证据，不能证明浏览器恰好采用了哪种底层事务交错，也没有覆盖配额故障、commit abort、断电持久性或所有升级阻塞场景。保存期间插入新编辑的延迟场景仍仅有受控 Promise 的边界测试，未冒称浏览器已覆盖。依据实测发现，保存结果另在顶部保存区以实时消息显示，并将过期基线提示译为中文，避免错误只出现在长页面下部。冲突截图位于父级 `docs/character-system-research/character-storage-conflict-2026-10-16.jpg`。
