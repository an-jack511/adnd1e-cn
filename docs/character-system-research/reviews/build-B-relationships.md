# Subagent B：核心关系账（随从、受雇者、忠诚与士气）构建报告

日期：2026-10-14。视角为“资深 AD&D 1e DM”的规则实践审查，不声称真实履历。本轮是有界实现，只修改用户指定的规则数据、引擎、独立测试和本报告；未修改 suite、package、UI、schema、角色档案或其他规则模块。

## 1. 结论

本轮建立了一个可供主 Agent 接入的核心关系领域骨架，但没有把它包装成完整据点或追随者系统。最重要的产品边界是：

1. `henchman` 与 `hireling` 不是同一个槽位。随从是有种族、职业、成长履历、冒险份额及长期关系的 NPC；受雇者是依合同提供劳动、专业服务或军事服务的人。雇佣兵属于受雇者，不因受薪而自动成为随从。
2. PHB13 的魅力人数上限只限制随从；它明确不限制雇佣兵、武装人员、仆役等。工具可以提醒随从容量，不能用同一上限拒绝聘用第十六名士兵。
3. 招募、合同、持续关系、忠诚检定和战斗士气是五种不同事实。一次招募成功不等于永久忠诚；工资已付也不等于在明显危险中必然服从。
4. DMG36–37 的忠诚是 `50% + 魅力忠诚调整 + 关系/待遇/情境修正`。DMG67 的战斗士气以当前忠诚值为门槛，但该页的正修正加在百分骰上、使检定更困难。两者不能共用一个“把所有加值相加到目标数”的函数。
5. 忠诚分数、真实候选人特征、招募骰、士气骰和 DM 笔记均为 DM 私有。玩家只能看到合同、已公开事实和已经在虚构世界中观察到的行为。玩家投影必须从公开字段白名单重新构造，不能复制 DM 对象后删除几个已知键。

## 3. 已实现的数据与算法

### 3.1 规则数据

`src/character/rules/core-relationships.ts` 提供：

- 带原件文件、哈希、印刷页/PDF页/index0 和核验方式的 citation 注册表；
- PHB13 魅力 3–18 的随从上限、忠诚基础调整和反应调整全表；
- `henchman`、`standard-hireling`、`expert-hireling`、`mercenary` 的关系分类；
- DMG35 随从最低初始报酬、金钱兴趣上限、可用魔法物品、住处与供养、魅力反应调整；
- DMG36–37 忠诚修正表，并标出可重复计数项目；
- DMG67 士气触发、骰值修正及失败差值结果；
- 未覆盖项目的 `unknown` / `needs-dm` 清单。

### 3.2 引擎

`src/character/engine/core-relationships.ts` 提供五组纯函数：

1. `checkHenchmanCapacity`：只供随从调用，绝不用于限制受雇者人数。
2. `evaluateHenchmanOffer`：验证每级至少 100 gp；计算金钱、可用魔法物品、供养和魅力反应；可不传 DM 私有 d100，只预览目标值。
3. `calculatePrivateLoyalty`：计算 DM 私有忠诚；限制互斥档位；特殊负项和正项分别只取最强一项；可重复情境按计数；允许有理由的 DM 人工调整。残酷/专横待遇会因领主是否在场且掌权而变号，调用者未明确裁定时返回 `needs-dm`，不会猜。
4. `resolvePrivateMorale`：将 DMG67 触发与战斗情境修正作用在百分骰上，再与忠诚基准比较；按失败差值给出坚持、边战边退、脱离撤退、恐慌逃跑或投降。
5. `projectRelationshipForPlayer`：从允许公开的合同和观察事件字段重新构造玩家投影，不复制 `secret` 对象。

## 5. 仍然阻断自动化的边界

以下事项没有逐格核验或不属于本轮页段，因此保持 `unknown` / `needs-dm`：

- 标准与专家受雇者全部职业、费用、产能、设施和可用人数表；
- 每种聚居地实际有哪些候选人、人口比例、种族与职业生成，以及候选人的真实属性、阵营、宗教和性格；
- 非人类/特殊种族魅力在具体对象上的有效值。PHB13 给出脚注，但自动选择“原始值还是受限值”还需要人物种族履历与对象种族上下文；本轮引擎要求上游给出最终用于该关系的魅力值，不擅自重算；
- `treatment-cruel` 在领主在场/失能/死亡时的符号选择；必须由 DM 提交已解析值；
- NPC 的种族偏好和结伴群体中“最喜欢/最厌恶对象”的选择；
- 职业高阶追随者、学徒、学生、盟友生物、召唤生物、家臣、军事指挥链和据点人口；
- 随从 XP、自己的训练、装备所有权、死亡/复活和跨地点日历。这些应引用人物履历、资源账及活动账，不能在关系模块生成第二份真相；
- 忠诚结果的公开程度。玩家观察到“拒绝冲锋”可以进入公开事件；“忠诚 42、掷出 73”默认不能公开。

未核表不可用 `0`、平均工资、现代 D&D 被动忠诚或一个通用“关系值”填补。主 Agent 接入 UI 时，应允许记录人工合同和裁定，而不是等所有表完成才允许建立关系；但页面必须显示相应字段仍未规则认证。

## 6. 主 Agent 接入建议与压力用例

1. 角色档案保存关系 ID 与对方角色/人员记录的引用；不要把完整 NPC 私档嵌进玩家角色导出。
2. DM 权威档保存私有关系记录；玩家文件保存带独立 schema/version 的公开投影。公开投影不得反向覆盖 DM 权威档。
3. 合同变更、付薪、欠薪、礼物、任务命令、忠诚检定和士气检定都应成为独立事件；撤销一次付薪不能静默删除之后已经发生的逃跑或公开冲突。
4. 忠诚重算使用当时事实快照。后来的待遇改善不能改写三个月前的检定目标值。
5. DMG37 明许有把握的 DM 直接扮演/裁定而不掷表。工具必须允许“DM 直接裁定结果 + 理由”，但不能伪造一个未掷出的 d100。

| 压力用例 | 正确边界 |
|---|---|
| CHA18 角色已有15名随从，又要雇100名士兵 | 拒绝新增普通随从；士兵人数不受 CHA 随从上限约束，转合同、可用性和军队组织裁定。 |
| CHA9角色用最低100gp但不供住食招一级随从 | 目标为0%；d100不可能成功。不是自动把概率夹到5%。 |
| 一项关系同时有杀害忠诚随从、传闻折磨、礼物和亲自救命 | 负项只取最重 -40，正项只取最高 +25；不把所有特殊项累加。 |
| 领主残酷但就在附近且掌权 | 不能直接套 -10；按原注可能作为 +10。未给状态则 `needs-dm`。 |
| 当前忠诚65，士气骰50，25%队伍损失+5且一名友军阵亡+10 | 调整骰为65，成功；不是把目标忠诚加到80。 |
| 玩家导出角色 | 可见姓名、合同、装备承诺与亲眼观察；不得出现真实阵营、忠诚目标、骰点、DM原因或秘密键名。 |
