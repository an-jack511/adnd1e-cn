## 2. DM 桌边判断：可靠能力应保留，缺口应显露

当前不是只有静态人物表。C2 已经把经验、训练付款、物资、施法消耗、生命状态和日历变成可重放行动；C4 使用 IndexedDB 同一读写事务中的比较与 put，存储 envelope 包含主件和最多五份旧件。不能建议重新建一套不兼容数据库，也不能误报为 localStorage 假 CAS。

H03 已有显式跨门槛评价复用，标为战役采用解释；H04 已有旧训练片段时间对账；H05/v2 已有后补冲突和历次完整休养复查；H06 已有相接训练地点边界核对。原型应调用这些既有接口并展示检查范围，而非重新用 UI 条件替代引擎。

旧存储评审中“保存中新增行动被已保存掩盖”“加载与文件导入交错覆盖”的描述已不符合本次 C5：`createCoreEditorIo` 串行化异步打开/保存，`savedSnapshot` 标识未保存进度，并区分已保存但列表刷新失败。这里仍需浏览器测试，但不能继续列为未修复确定缺陷。

### B01 / P1：长档案可能被自己生成的行动锁住

源码确认：C2 的 parse 拒绝超过 10,000 条行动；commit 只检查输入档案，再追加行动并 replay，未对输出行动数设置同等上限。合法 10,000 条档案再成功提交一次，得到的 10,001 条结果会被下一次 parse、保存或打开拒绝。这是控制流确定的不对称，未实际构造满额档案。

另一个边界：C5 文件导入上限 8 MiB，导出没有对应限制；C6 隔离检查上限 2 MiB，且不提供运营重放。故“超限请用档案检查页”不能保证有可走通的继续游玩路径。C2 每步把包含增长中历史的完整模块放入事件，C4 另保留多份完整档案，存在体积和重放成本放大；尚未测量，不宣称具体性能数字。

验收前门槛：成功提交必须保证结果仍可由同版本重新打开与保存；接近边界预警并提供可用导出。超过边界时输入及存储均不变。后续日志分段/检查点须另做格式设计与迁移，不能静默删历史。

### B02 / P1：文件可保全，但续玩与恢复流程未闭合

源码确认：从文件打开同角色同分支时没有建立本地基线，`savedToken` 起始为 null；保存遇到已有槽会冲突。C4 返回 `conflict.current`，C5 只显示 reason。即便导入文件是合法后续，也没有谱系比较后接续保存的界面。

历史恢复目前是候选导出，保留原 branchId；没有通过准入和重放建立新分支的 UI。旧件不能直接覆盖主件是正确约束，但“恢复”按钮必须说明它只导出候选。原型需要演示双方版本比较、双方导出、明确选择保留本地/另建分支；不能靠更新 token 绕开分歧。

### B03 / P1：纠错不能等价于治疗、逆向记账或删事件

源码确认：当前 CampaignAction 没有通用纠错/撤销命令；已准入创建又明确禁止改写。DM 把伤害 3 录成 30、选错钱包、事后发现旧训练地点错误，都缺少统一的可继续操作路径。`settle-current-hp` 是受限的待裁定 HP 结算，不能当成通用“改回正确值”。

产品建议：区分取消未提交草案、追加外部补偿事实、历史事实纠正、另建分支。前者不产生事件；实际治疗/退款保留其事实与来源；历史纠正引用错误行动，列出依赖它的授级、休养、消费等后果，预览重建差异后显式处理。不支持安全修复的情形提供保全与分支，不能显示一个实际只改快照的“撤销”。这需要后续工作流设计，本轮不承诺已有完整纠错算法。

### B04 / P1：四视图不应制造第二份真相

旧 `/character/` 明示是未接事件档案的手工表，仍以 `adnd1e-characters` / `adnd1e-character` 保存自由字段。它的 XP、HP、法术文本不能直接作为新 sheet 的可运营事实。C2 `base` 只接受单一普通核心职业，排除 Bard；创建可表达多职业不代表运营适配器也支持。

四个视图必须共享同一角色、分支、revision 和只读投影；unsupported 职业或来源要显示“可查看，当前不可执行此流程”。不要以四个页面看起来都有内容，冒充所有职业生命周期已接通。

### B05 / P1：有日历区间不等于有统一战役现在

源码确认：C3 只有单位与角色活动区间；C2 阻止再次 configure-calendar，普通 schedule-activity 必须属于本角色。未见共享 campaignId/历法纪元/多角色主时钟或所有普通行动的结构化生效时点。C5 的 `actor.at` 是任意非空文字，与数值分钟不一致也不会自动建立统一关系。

H06 只检查同课程相接片段，不能证明此前冒险到首次训练的移动，也不能保证先授级后补记过去施法时使用的是当时能力。日历首先显示“已记录活动”，不要把最后一个区间终点自动称作当前世界时间。

建议：展示战役历法、角色最后确认时点、活动发生时点、录入时间四种含义；允许有标记的后补事实。历法先作为既有分钟轴上的显示与配置引用，月名、闰日、纪元属于战役设定，不能硬编码现实七日周或凭空换算旧数据。多人共享时钟、历法更换及全历史位置核对另设版本化方案。已记录单位不得只换标签后重解释旧分钟。

### B06 / P1：DM 标签和可见性字段不是授权系统

C1 接受非空 actorId；C8 `authority:'dm-ruling'` 也是输入数据，不证明真实 DM 身份。静态本地工具可以明确是“记录裁定者标签”的信任模式；不能宣称阻止玩家伪造裁定。以后多人服务需要可信边界，不能提前把隐藏按钮当权限控制。

C2 把运营整体放入 `visibility:'player'` 模块，其中包含 calendar 的裁定理由/来源。C6 的公开投影只按模块筛选，不会自动净化每个嵌套字段。尚未发现现有秘密关系数据已泄漏，但若将研究成功条件、忠诚或私密关系账本直接接入该模块，就有明确泄漏通路。PL 投影需字段白名单；DM 私密数据不得进入 PL 导出、打印、搜索、DOM 或错误提示。能离线续玩的公开便携账本与只读公开摘要也必须区别命名。

### B07 / P2：操作表单仍容易选错对象，缺少长期循环

C5 `render()` 重建钱包、物品、位置和准备副本选项；部分已有选择保留逻辑不能覆盖这些对象。施法副本标签按剩余列表重新编号。DM 在另一操作后继续旧表单，可能作用于首项。建议按稳定 ID 保留合法选择，提交前显示实例、钱包和前后差值；对象已失效则要求重新选择，不能悄悄换成同名对象。

C2 当前行动表有 `cast-prepared`，未接普通重新准备/祈祷、一般治疗与死亡后复生的完整运营入口。引擎有能力不等于界面可操作。sheet 必须显露这些循环的支持范围，不能“过一天”就重置副本或 HP，也不能把 Heal 特例当普通治疗。

C8 的关系付款只记外部账，不扣钱包或推进日历。若接入，必须明确“登记已付收据”与“从钱包付款”；后者需要同一事务记账并扣钱，避免两边半成功。归队、重新雇佣、复生的未支持状态不能冒称 RAW 永久禁止。

## 3. 建议的稳定 Action 层：适配现有引擎，不另建规则系统

四视图只提交 intent，由统一目录描述 label、支持范围、必要输入、目标对象、检查来源、裁定需求、公开摘要。适配器继续调用现有 creation / admission / campaign / calendar 工作流；不能把新写入口接到允许旧语义的 replay API。

建议生命周期：草案 → 只读预览 → 确认事实与裁定 → 内存提交 → 持久化结果。预览使用克隆及相同工作流，输出确定的前后差值、阻断理由、待 DM 事实、规则状态、日历占用与依赖。预览不得写库、推进游戏时钟或重新掷骰；已掷骰面及选择固定在草案。关闭预览不产生事实。

提交绑定 actionId、characterId、branchId、expectedRevision、目标稳定 ID、实际骰面、来源、裁定理由及检查政策。预览期间 revision 变化必须重新预览，不能静默改基线。重试沿用 actionId；C1 有收据幂等基础，但仍须验证 campaign 包装器，不可仅因底层有 receipt 就宣称整个操作幂等。双击生成两个 UUID 是两个不同请求，UI 也需防重复。

“已记录”与“已保存本地”分别显示；文件下载只表示请求下载，不能宣称外部备份已落盘。合并扣款、训练付款等同一业务操作时失败全部不变。跨角色交易在没有跨档案原子协议前标记不支持，不能分别提交两次后称作转账成功。

对可用性采用 `available / blocked / needs-dm / unsupported / historical-only` 等内部状态，并翻译成人能理解的理由和下一步。规则证据、战役采用解释、软件检查策略是三个维度：`consequencePolicy=v2` 不是 AD&D 版本，`locationPolicy=v1` 也不是全部 RAW 的认证标记。

## 4. 四个原型必须共用的 DM 场景

延续 `src/styles/global.css` 的白底、深灰字、酒红链接（#6b1d1d）、灰线和衬线正文；不引入装饰纹理掩盖状态。操作区使用清晰表单字号。色彩仅辅助，错误/待裁定/未保存均有文字。以下是设计要求，尚无实际屏幕测量。

| 视图 | 必须可交互的任务 | 对 DM 的关键证据 |
|---|---|---|
| create | 属性批次 → 身份选择 → 创建任务 → DM 审核 → 准入预览；改变身份后显示需重做任务 | 骰面与方法保留；理解/取得/准备分列；未解决事项不被“完成”按钮掩盖 |
| sheet | 从同一正式档案查看资源；选择物品/副本/钱包并预览一次消耗或伤害 | 具体实例和差值、生命限制、提交/未保存状态；不能任意覆盖等级或 HP |
| growth | 已结算 XP → 候选 → 评价与费用 → 付款 → 实际日历 → 门槛 → 单次授级 | 每项阻断可追溯；旧片段对账、溢出采用、后果与地点检查各自独立 |
| journal | 按发生时间/录入顺序切换；查看行动、来源、裁定和影响；打开纠错/分支比较草案 | 后补不伪装成当时已知；普通叙事笔记不自动授 XP、改变库存或认证事实 |

共享页头持续显示角色、分支、revision、支持范围、未保存状态和角色已确认时点（未知则写未知）。journal 不另存一份可覆盖角色事实的日志数据库；普通笔记若需新增正式模块，应后续定义版本与可见性。

桌面允许主工作区加摘要，窄屏按任务顺序单列；确认面板不遮住差值或取消入口。验收至少覆盖 360 / 768 / 1280 CSS px、200% 缩放、键盘完整操作、焦点返回触发按钮、状态播报、长中文来源和多个同名实例。攻击矩阵可局部横向滚动，不以 THAC0 线性简化代替已核重复20。

原型可用同一合成角色分支模拟，明确标注演示数据及尚未接入的行动；不写生产档案。四张孤立截图不能满足此 Phase A 的交互验收。

## 5. 便携文件与迁移：先承认当前格式分层

| 当前层 | 实际标识/存储 | 迁移约束 |
|---|---|---|
| 旧手工表 | localStorage `adnd1e-characters` / `adnd1e-character` | 仅旧断言，不能补造骰面、钱包、书本或准入 |
| 属性草稿 | `adnd1e-creation-draft` 1.0.0；`adnd1e-creation-library-v1` | 保留原批次和派生谱系，不等于正式角色 |
| 核心创建 | `adnd1e-core-creation` 1.0.0；`adnd1e:core-creation-library:v1` | 已准入不可覆盖；候选和任务状态不能凭字段复制认证 |
| 准入/运营 | `adnd1e-core-admission-runtime` / `adnd1e-core-campaign-runtime`，schemaVersion 为数字1 | 由各自解析器重放；不是通用候选1.1格式 |
| 本地运营 envelope | `adnd1e-core-campaign-storage` 1；IndexedDB `adnd1e-campaign-runtime-v1` | token/generation/history 属存储协议，不能直接当便携角色导入 |
| 通用候选/投影/隔离 | character 1.1.0 等；IndexedDB `adnd1e-character-archives-v1` 当前打开版本2 | 结构检查不等于规则或准入认证；与运营库并存 |

源码确认：C6 的通用隔离识别分派未包含上述 core-creation/core-admission/core-campaign 格式；schemaVersion 摘要还只接受字符串。不能把“统一导入”现有入口称为所有当前文件的完整验证器。

Phase A 应设计统一文件选择后的分流预览：原始字节/文件大小 → format 与版本识别 → 对应解析器与诊断 → 查看/隔离/导入草案/打开运营/比较本地。保持现有格式与存储，先做适配器，不创建第三套可玩角色格式。若未来需要便携外壳，必须单独提交版本决策与迁移样例，不能直接改现有 schema。

迁移应输出新候选与前后差异，保留原字节及来源映射；schema、行动语义、检查政策和引擎兼容范围分别记录。当前没有完整固定引擎版本支持，不能编造版本哈希代表可重放认证。未知字段/版本保全，公开投影不升级为私密可玩档；旧 v1/无标记行动可历史读取，不因迁移而冒充通过当前新写策略。重复导入按身份与谱系比较，不按文件名覆盖。

## 6. 硬生命周期验收（待执行，非通过清单）

| ID | 操作链/故障注入 | 必须可观察的结果 |
|---|---|---|
| L01 | 创建 → 准入 → sheet 消耗 → growth → journal → 保存 → 关页重开 | 四视图同身份/分支/事实；重开重放一致；未准入与不支持职业不进入假运营 |

## Round 2：对 A/C 的交叉批评与收窄后的原型合同

日期：2026-10-16。完整阅读 [A 历史设计评审](phase-a-historical-review.md) 与 [C 玩家任务评审](phase-a-player-review.md) 的第一轮文本。本节仅追加本人评审，未修改其他报告、未实施代码或执行测试。以下针对用户提出的隔离原型方案调整第一轮意见；原书证据等级仍沿用前文，没有新增原件核验。

### 对其他两份报告的具体批评

**B-R2-01：A 的“已准入角色”与多施法传统要求超出了当前原型，也可能诱导假准入。** A 的开头建议“一个已获准入的普通单职业核心角色”并额外提供 MU、幻术师、神术差异；AT05/AT10 又要求副本恢复与零 HP 情境。当前明确只用一个内存合成角色，禁止宣称已准入，复杂恢复也不实现。若为了满足这些场景而伪造准入戳或新增恢复状态机，反而破坏 A 自己提出的证据边界。建议 A 将这些条目分成“原型必须表达的限制”和“生产必须通过的引擎场景”。本期可以用单一合成 MU 展示法术分层，对其他施法传统显示范围说明，不需要实现其生命周期。但我保留一项要求：不支持恢复的提示必须在副本耗尽后的任务位置出现，不能只放说明页。

**B-R2-02：A02/AT09 把复杂阻塞的可操作演示当作必需，缺少支持接口的区分。** 缺日期、异地相接、后补旅行是有价值的生产情境；但本期只承诺训练计算器，不承诺调用完整日历/授级工作流。静态阻塞样例可以解释设计，却不能称“已执行现行授级校验”。建议本期只演示真实调用计算器的输入/结果，以及“这不是课程已付款、已占时或授级”的明确边界；若仍提供日历冲突样例，标为说明夹具，不生成声称训练完成的事件。我保留对时间成本的要求，不要求本期建立统一世界时钟。

**B-R2-03：C 第7节的四类夹具与多角色入口应当收窄，但单角色会损失真实任务覆盖。** C 要求有效战士、有效施法者、未完创建、旧记录/冲突四种状态，并在第3节设计角色选择、文件打开和正式四路由。这与本期一个合成角色、hash 四视图、拒绝真实导入不一致。应将旧记录冲突、切换档案、生产保存从本期验收移出，不能只画一个实际上无功能的“继续本地角色”。不过单 MU 无法验证战士训练阶段、跨职业差异和多个档案辨识；四视图成功只证明单样本的导航和局部事务。建议 C 保留这些未覆盖项为明确结论，而非因流程变短而宣布玩家主任务均验证完成。

**B-R2-04：C 的“三次交互”与错误恢复指标需要同时衡量。** 第4节将“一组填写”整体计一步，可能把钱包选择、来源、DM理由及差值阅读的实际负担隐藏；它不足以比较两个设计。建议测试时同时记录选择对象是否正确、预览中能否发现错误、取消是否保留输入、确认后能否找到日志，以及实际所需字段。正常路径三步可以作为导航目标，不能作为压缩规则事实的约束。C 关于稳定对象、焦点返回、错误邻近输入的要求保留；本期无本地保存，状态条应改成“仅本页内存 / 已请求导出演示文件”，不能复用“本地已保存”。

### 修改本人的第一轮门槛

撤回前文把 L01 的正式准入、L05 的完整后果裁定、L10 的真实档案恢复及 L11 的依赖历史纠错都列为本期必须走通的要求。本期不读取真实档案，不以合成事件替代正式 runtime；这些条目继续作为生产接线要求，未获解决或验收。

同意将原型放在隔离的 `/character/prototype/`，以 `#create`、`#sheet`、`#growth`、`#journal` 寻址四视图，使用一个内存合成角色。复用已核 DMG 属性生成、资格、起始 MU 法术及金钱/HP/训练计算器；原型 reducer 只负责演示状态与事件，不另抄规则算法。正式生产行动仍走现有 parser/commit，不由这个 reducer 接管。B01–B07 对生产的发现保留，不能因为原型隔离就标为已修复。

这种收窄可以验证导航、变化预览与失败反馈，不能验证跨窗口 CAS、配额、权限、真实档案兼容及持续战役重放。Phase A 结果需分别记录“已演示”“未执行”“范围外”，不把原型操作通过写成上述生产缺口已关闭。

### 对主方案仍保留的疑问与明确要求

**1. 只用一个 MU，但训练计算器未必覆盖该 MU 的成长。** 如果演示角色尚未完成创建，sheet/growth 应显示“合成演示状态”，不能让创建任务一完成就出现“已准入”。修改职业或属性时预览哪些下游演示结果失效，取消保留原结果；接受后只让既有资格/资源计算器重算。训练计算结果明确绑定当前演示职业与等级，不能拿战士已核样例作为 MU 的费用或成长认证。导师、实际交费、实际训练、授级彼此分开；若未接完整流程，提供计算与计划，不改变正式意义的等级/能力。

**2. preview → atomic apply → event 必须说明“原子”只到内存对象。** 先在隔离候选上检查全部输入与业务效果，成功时一次替换状态与事件集合，失败则二者及 revision 均不变；不能先扣钱再发现法术不合法。预览固定对象 ID、骰面和基线 revision；另一演示行动发生后原预览失效。动作确认和组件重绘都不能重新掷骰。这里没有持久化或跨角色原子性，不使用“事务已永久保存”的文案。

**3. 只撤销最后一个合成行动是合理边界，但不能把它包装成历史纠错已完成。** latest 按全局合成行动提交顺序定义，四视图、筛选和排序都不能改变它；浏览器后退不是 undo。撤销一次应恢复该行动前的完整业务状态（资源、副本、下游计算、草案关联），而非只恢复屏幕上的 HP 数字。建议日志保留“行动已撤销”的演示痕迹，并保留单调变化的编辑 revision，使旧预览失效；明确不支持再次撤销更早行动或 redo，直到新的演示行动提交。若选择直接弹出事件的更简实现，须明确日志不是不可变审计链，这是与生产事件历史的实质差异。撤销不能用于重掷求更好结果；骰面保留，重新掷骰须是明确的新动作。

**4. 零 HP 和复杂恢复不能只藏掉按钮。** 当一次伤害将 HP 推到0或以下，停止本次 apply，显示具体范围外原因，保持原状态与事件不变；不能钳到1、只记0而遗漏昏迷/流血，或显示为合法的纯减法成功。没有恢复入口时，用尽副本后显示“本原型不演示重新准备”，不能日刷新。研究仅生成 proposal，日志标“提案，未结算”；不扣钱、不占实际日历、不增加法术、不掷秘密成功检查。普通叙事和 proposal 的数量不应计入已执行资源行动数。

**5. 演示文件与真实档案必须双向隔离。** 导出使用独立、明确的 prototype format/version，并包含 synthetic 标志与支持范围，文件名可辨认。不得套用 `adnd1e-character`、准入或 campaign runtime 标识。真实导入尝试应在修改内存前拒绝，保留现有角色/草案/事件；演示文件也不能被生产入口误认成正式档。是否支持演示文件回读需明确：若不支持，导出说明“供检查，不可恢复会话”，不能承诺刷新后继续。导出按钮不等于文件已落盘。

**6. schema 1.1 统一格式只能作为设计提案，有额外字段并不等于现有契约可接受。** 选择已有 schema 1.1 是比再造生产格式更明确的方向，但前文所列 core creation/admission/campaign 与 storage envelope 各自语义不同；没有 adapter 与逐项往返样例，不能称它们已经统一。需要提案提供旧格式→目标字段/保留载荷→回导原件的映射表，区分原始字节保全与迁移后可运营等价。完整内嵌原件会增加体积且可能携带 DM 私密内容；“无损”与“公开安全导出”不能合用一条不分层的承诺。若1.1当前schema不容纳所需数据，必须列为契约差距，不能未经版本决策硬塞字段或把原件降格成无人校验的备注。适配器后做意味着本期没有完成迁移，不能给现有档案加“迁移安全”状态。

**7. hash 可寻址不等于状态可恢复。** 四个hash应支持复制地址、直接打开、前进/后退并将焦点移到当前视图标题；未知hash回到明确默认页。切换不发事件、不消耗资源、不重掷、不丢未提交输入。刷新后内存丢失是方案的真实代价，首屏与导出旁均需说明；直达 `#growth` 不能暗示URL包含上次成长结果。若提供“重置演示”，应说明将清空本页状态并可取消，不能用导航链接暗中重置。
