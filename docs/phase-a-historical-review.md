# Phase A 第一轮独立审查 A：历史设计与规则边界

日期：2026-10-16。范围：创建 create、人物卡 sheet、成长 growth、日志 journal 四个响应式交互原型的设计审查；不是实现交付，也不是全规则认证。

## 立场、证据与结论

本文是历史设计模拟：借助已核原书证据评估是否保留 1e 的时间、资源、职业差异和 DM 裁判地位，不是假托 Gygax 本人的证词、意见或访谈。以下建议属于审查者的产品判断，不因采用历史视角而成为原书规则。

结论：四视图方向可继续，但进入大规模实现前，原型必须演示“资格不等于授予、时间经过不等于活动完成、事实登记不等于保留规则利益”。不能把现有引擎改造成统一的即时升级、通用已知法术列表或一键长休模型。建议以一个已获准入的普通单职业核心角色贯穿四视图，并额外提供魔法师、幻术师、牧师/德鲁伊的差异情境；多/双职业及扩展保留真实可见的覆盖边界。

证据等级：

- **S：共享已核书证**。已阅读指定的[共享证据台账](../../docs/character-system-research/shared-evidence.md)，引用其中 E 编号及明确给出的印刷/PDF 页码。本文未重新查看原书页图，不声称亲自完成其视觉核验。
- **D：已有补证/决策报告**。已阅读本文链接的报告；其中原页核验由报告署名者承担。D 不能自动提升为本文重新核验的书证。
- **C：本轮静态代码观察**。已读取本文列出的源码，能够确认接口和分支存在；未运行测试、未操作浏览器，不能据此认证交互、全部算法或测试通过。
- **U：未封口**。证据不足、书间关系待采用、算法范围外或端到端未验收，须在设计中保留，不补猜页码。

本轮仅新增本文；既有工作区包含其他人的修改，未更改实现或既有文档。原型本身尚未在本轮创建或验收。

## 需要在设计阶段解决的具体问题

**A01 / 高：把动作结果当作人物完整认证。** 当前旧人物记录页与新准入/运营页并存，保存成功、无已检查冲突、通过导入和已授级各自只证明有限事实。四视图应在人物标题附近显示当前阶段、规则包和可用范围；主按钮采用“提交审核”“记录付款”“请求授级”等实际动作。不能让一个绿色总状态替代全部资格、训练和法术取得。

**A02 / 高：时间成本在简化 UI 时消失。** 训练周数、日历覆盖、授级时点、活动后果必须是可追踪的同一事实链。日期输入不应默认现实今天；“记录为过去活动”须与“现在获得利益”区别显示。原型至少演示缺日期、异地相接、事后补记旅行三个阻塞情境。日历检查策略 v1/v2 是软件历史策略，不是 1e/2e 的版别选择。

**A03 / 高：法术被容量面板吞并。** `deriveCoreGrowthChecklist` 已明确容量变化不授予法术；当前 runtime 只有公开副本消费等有界入口，不能用一个准备按钮暗示完整取得/休息/学习/材料/效果均已自动验证。原型必须展示合法分层和未接通路径。可操作的模拟步骤标为演示，不能产出看似真实完成的运营档案。

**A04 / 高：普通 DM 理由被当成覆盖已知规则的万能许可。** 事实裁定、原书授权选项、书间采用解释、违反已知规则的本团例外应各有文字身份。训练费偏离公式、子职业费用族采用、XP 溢出评价复用尤其要保留身份和来源；仅有 reason 字串不足以向用户宣称全部是 RAW。导师存在、职业/等级和实际可用性未结构化证明时，应明确显示人工确认范围，不能“钱够就有导师”。

**A05 / 高：将 DM 私密信息藏在折叠区就当作隔离。** 玩家页只读取公开投影；秘密研究、神授原因、忠诚/士气等不得预载进玩家 HTML、可访问性文本或玩家导出。现有法术领域白名单只是支点，不是四视图整合后的泄密验收。DM 姓名字段也不等于身份认证或远程多人权限系统。

**A06 / 中：经典外观影响可用性，或被误作历史真实性。** 当前 `src/styles/global.css` 已有白底、深灰正文、暗红链接及细灰表格线，可作为参考色系（#fff、#222、#6b1d1d、#aaa）。四视图采用清晰栏目、可展开来源与可打印人物卡即可；不用暗色仪表盘或装饰性羊皮纸承担规则可信度。小屏不能通过隐藏资源、限制和来源缩短页面。触控尺寸、对比度和断点是本轮产品建议，尚未实测达标。

## 四视图的最小交互合同

| 视图 | 必须看见与可以操作 | 必须演示的失败/待裁定状态 | 复用边界 |
| --- | --- | --- | --- |
| create 创建 | 先选战役来源，依方法看骰点/分配、资格和起始资源；阶段完成度及继续审核入口 | 缺少必要事实；禁起始法术；扩展冲突待采用 | 复用 `core-create`、资格规则及起始法术控制器；不另建人物数据库 |
| sheet 人物卡 | 当前已获等级、五类豁免、攻击表、钱包/携带物、HP 限制、逐份准备副本；操作前可看具体消耗 | 未知重量、组件待判、同名但来源不同、HP 恢复而休养禁令仍在 | 从已验证档案与公开投影派生；不把旧自由表单当作运营事实更新入口 |
| growth 成长 | 已获等级与下一候选并列；评价、路线、费用、实际付款、训练日期、门槛、授级后待办 | XP 足但训练不足；严重中断；多阈值采用解释；导师待确认 | 复用 advancement、stage、dated training、overrun、growth checklist；不能绕过 runtime 新写入口 |
| journal 日志 | 战役时间与实际记录时间分列，人物/地点/活动及费用关联；按训练/休养等过滤并回看来源 | 旧无日期记录；后补冲突；未知来源；未完成研究 | 读现有行动、事件、calendar 及历史选择器；不重存第二份可编辑 XP/钱包/训练总数 |

桌面可将状态与来源放在侧栏，小屏按“当前状态→本次操作→阻塞原因→历史/来源”堆叠。宽攻击表可独立横向滚动并保持列标题，页面主体不横向溢出。四视图切换保留同一人物及未提交草稿；查看、筛选、打开来源不掷骰、不扣资源、不自动发事件。交互原型应使用内存中的明确模拟状态，接真实数据的动作才使用现有事务入口；不新增不兼容存储格式。

### 对主方案的保留意见及要求

**R2-A / 训练计算器不等于训练完成程序。** 这是范围收敛后最重要的规则风险。已有 `core-training.ts` 可产生周数/费用，`core-training-stage.ts` 可判断当前已获名号阶段，但它们自身不证明导师存在、实际付款、连续课程、地点事实和授级时点。若 growth 只调用这些计算器，则原子应用的业务事实应叫“保存演示训练计划”，journal 事件应叫“演示计划已记录”；不是“训练完成”或“等级已授予”。用户可以看到真实公式和资源预览，但不能从一个价格计算跳到新等级/HP/新法术。本期可以保留假设完成后的只读效果对照，必须标为假设，不应用到当前人物。

**R2-B / “应用→事件”的原子性不能只覆盖数值。** 原子应用必须一次替换人物事实、演示事件及该行动的撤销依据；其中任何一步失败均保持应用前状态。草稿记录稳定行动 ID、基线修订、目标实例及原骰，预览和确认使用相同输入；预览不重掷，hash 切换不提交。即便只有一个人物，另一视图应用行动、重新生成属性或撤销都可能使旧预览失效，不能因为没有多人就省略基线检查。这是演示一致性要求，不声称已有生产事务整合。

**R2-C / 最新一步撤销可接受，但不能塑造错误的时间和资源直觉。** 我撤回第一轮把纯查看日志一概限定为正式不可回退事实链的潜在外推：本期允许回退最近一次合成行动，便于评审尝试；它不是 DM 对世界历史的纠错功能。按钮应写“撤销最近一次演示操作”，并恢复该行动的所有资源/任务联动。不能把撤销伤害记成治疗、撤销付款记成退款，或把它显示为原书授权。

撤销随机生成尤其有代价：回到前态后重新点生成会让评审挑选更好结果。原型可允许明确的“重新掷骰演示”，但要区分恢复原骰与新生成；撤销后不能无提示地产生新骰，或宣称这些挑选结果符合既定战役生成程序。撤销覆盖一个业务行动的全部演示事件；不要求本期再实现完整多步撤销栈。若 A 后有 B，再撤销 B，A 不应因此获得连续第二次撤销入口，除非以后明确改变“仅最近一次”的合同。另做新的操作可以撤销该新操作。

为免 journal 把已撤销效果仍显示为当前事实，可在演示事件行标记撤销，另保留前后快照用于一次回退；也可采用明确的演示回退展示策略。两者都必须清楚区分当前有效事件与回退说明，不能假装有正式历史修复协议。导出若保留已撤销行，亦保留其非生效身份。

**R2-D / 明确 unsupported 必须发生在边界之前。** 零 HP 不支持，不能允许伤害先降到 0 再仅显示“不支持”，也不能自动钳为 1 HP 或改为死亡。应预览并阻止越界效果，保留原 HP/日志，解释本原型不处理该流程。复杂法术恢复同理：显示规则依据和缺口可以，不能用跨日按钮补回已消耗副本。研究提案只能改变提案列表/状态，不扣研究费用、不占为已发生的研究时间、不掷秘密成功骰、不生成法术/书内条目。若展示估算，必须与钱包和真实活动合计分离。

这使 sheet 的持续可玩性很有限：消耗后没有完整恢复循环，伤害接近 0 时流程会停止。我接受这项本期取舍，但保留异议：不能据此认为人物卡的日常循环已经验证；评审应记录用户是否理解为何停止，以及去哪里查看后续范围，而非仅统计正常路径成功率。

**R2-E / 一个 MU 的一致性与跨职业验证不能兼得。** 单一合成人物让四视图同步可验证，也降低重置和身份切换复杂度；相应地，幻术师、神术、战士重复 20、武僧名号、Bard、多/双职业只可列覆盖说明或独立资料，不得变成该人物的可用能力。第一轮 AT03 的幻术分支、AT05 的神术、AT06/AT11 的战士情境在本期不标“通过”；保留为以后职业情境验收。历史完整性此时靠诚实边界，而不是一个人物演完所有职业。

**R2-F / 原型 envelope 与 schema 1.1 是两件事。** 本轮补读 `character-v1.1.schema.json` 的标识及 `archive.ts` 检查接口：既有 schema 的标题明确为 design candidate 1.1，标识为 `adnd1e-character` / `1.1.0`；检查返回还明确 `fullSchemaValidated:false`、`rulesValidated:false`、`admissionValidated:false`。因此复用它作为未来统一格式的提案，比创建第三套生产角色格式更合适，但不能称其已经统一或可完整续玩。

原型导出须有独立 format/版本、合成数据身份、支持范围与有效/撤销演示动作的明确含义，不复用正式 format 标识，不生成准入凭据，也不把演示事件伪装成 runtime 行动。拒绝真实角色导入是正确隔离，代价是本轮无法检验迁移的易用性与保真度；不要求增加原型文件重导入，若未实现应直接说明导出仅供检查，不能承诺恢复。

“既有档案无损保留”仍需要后续适配设计证明，不能靠一份解析后的 JSON 或把版本数字改成 1.1 完成。原始字节、未知字段、旧行动顺序、来源与裁定、检查策略及身份谱系都须可保全；包装/引用原档不等于获得新格式的运营语义。正式新动作继续由对应 runtime parser/commit 处理，不能向 1.1 的 events 数组直接追加一条就当作实际游戏操作。本轮不要求实现这些适配器，也不授予迁移通过结论。
